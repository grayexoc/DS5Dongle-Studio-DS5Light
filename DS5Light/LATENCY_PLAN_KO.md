# 지연 개선 적용 및 후속 계획

## 이번 소스 적용

1. **프로세스 캡처 데이터 도착 알림**
   - 기존 2ms 간격의 Python 반복 확인을 조건 변수 알림으로 대체했다.
   - 데이터, 오류, 종료 시 대기 중인 소비자를 깨운다. 100ms 대기는 알림 누락과 취소에 대비한 보조 제한이며, 패킷마다 100ms를 기다리지 않는다.
   - 정지 버튼도 대기를 즉시 깨운다. 장치 전체 캡처의 대기 방식은 그대로다.
2. **출력 준비 시 과거 오디오 정리**
   - 출력 스트림이 준비된 시점에 프로세스 캡처의 누적 데이터를 한 번 정리한다.
   - 파이프를 통해 뒤늦게 도착하더라도 준비 시점 이전에 수집된 패킷은 제외한다.
   - 재생 중에 임의로 추가 폐기를 하는 정책은 도입하지 않았다. 기존 60ms 수집 시각 기준의 오래된 데이터 처리와 큐 용량 8은 유지한다.
3. **시각과 샘플 위치 추적**
   - WASAPI 첫 샘플의 QPC 시각, 네이티브 수집 시각, 프레임 위치와 플래그를 별도로 전달한다.
   - 부분 읽기와 패킷 경계를 넘어갈 때 남은 첫 샘플의 시각 및 위치를 보정한다.
   - 캡처 시각이 유효하지 않으면 해당 계측만 제외하고 오디오 전달은 유지한다.
4. **PC 내부 진단**
   - 네이티브 수집부터 Python 읽기까지의 대기, 캡처 첫 샘플부터 출력 호출까지, 출력 함수의 대기 시간을 각각 기록한다.
   - 각 항목은 최근 512개 표본의 p50/p95/max로 표시한다. 통계 계산과 화면 갱신은 기존 진단 표시 경로에서 수행한다.
   - PC 수신 버퍼 수치는 Python의 대기 데이터만 포함한다. 네이티브 큐와 드라이버 버퍼는 포함하지 않는다.
   - 출력 함수 대기 시간은 드라이버 재생 지연과 다르다. 표시되는 수치들을 더해서 전체 지연으로 취급하면 안 된다.

새 네이티브 프로토콜은 DS5T이며 이전 DS5P도 읽을 수 있다. 이전 헬퍼 실행 파일을 사용하면 첫 샘플 기반 캡처 지연은 표시할 수 없다. 새 프로토콜은 다음 빌드에서 헬퍼와 함께 반영된다.

## 기대 효과와 한계

- 반복 확인에 따른 깨우기와 도착 후 다음 확인까지의 대기를 줄일 수 있다. 실제 총 지연 감소량은 아직 측정하지 않았다.
- 시작 및 재연결 때 이미 지나간 오디오를 재생할 가능성을 낮춘다. 처음 시작할 때 짧은 구간은 생략될 수 있다.
- 48kHz/480프레임의 기존 10ms 전달 블록, 필터 알고리즘과 Pico 펌웨어는 변경하지 않았다.
- USB, 블루투스, 컨트롤러 내부 처리 및 실제 진동 개시 시각은 이 진단에서 측정하지 않는다.
- 이 단계는 소스 적용이다. 실행 시험, 하드웨어 측정 및 빌드는 수행하지 않았다.

## 후속 우선순위

| 순서 | 방법 | 적용 조건 / 고려할 문제 |
| --- | --- | --- |
| 1 | 동일 게임·동일 장치에서 새 PC 진단 수치 확인 | PC 내부 대기와 출력 함수 대기를 구분한다. 실제 진동 개시는 별도 동기 계측이 필요하다. |
| 2 | 출력 WASAPI의 지원 주기와 실제 버퍼 상태 조회 | 읽기 위주 진단부터 추가한다. 드라이버가 제공하는 최소 주기와 실제 동작 주기는 다를 수 있다. |
| 3 | 지원 장치에 한해 짧은 공유 모드 출력 주기 선택 | IAudioClient3 등 별도 출력 경로 검토가 필요하다. 지원 불가 시 기존 경로 복귀와 끊김 판단이 필요하다. |
| 4 | 5ms 블록을 선택 가능한 방식으로 도입 | 캡처 패킷 주기와 출력 주기가 허용해야 효과가 있다. 호출 횟수·스케줄링 부담 증가와 언더런 가능성을 확인한 뒤 기본값 변경 여부를 결정한다. |
| 5 | 오디오 작업 스레드 MMCSS / 네이티브 전송 개선 | 앞 단계에서 스케줄링 또는 파이프가 실제 병목인 경우 진행한다. Python 작업 간 경합과 프로세스 격리를 함께 검토한다. |

짧은 지연을 위해 큐와 오래된 데이터 기준을 일괄 축소하거나 시스템 타이머 해상도, 실시간 프로세스 우선순위, 펌웨어를 강제로 바꾸는 작업은 이번 단계에 포함하지 않는다.
